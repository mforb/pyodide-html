: Square root by repeated guessing

Difficulty: ★★☆


Plan first: draw the square-root flow chart using start/end, input/output, process and decision symbols. Label the decision's Yes and No arrows. Trace the starting guess and the first two updates in a table with columns guess, abs(guess * guess - x) and repeat?. Write plain-language steps before coding.

Instructions: find the square root without sqrt() or x ** 0.5. Start with guess = x / 2. While abs(guess * guess - x) > tolerance, improve the guess using guess = (guess + x / guess) / 2. Print the final root to six decimal places and whether its squared error is within tolerance.

This version assumes x > 0 and tolerance > 0. The tolerance applies to the squared error, not directly to the error in the root. Keep full precision during the calculation.

Expected output:

Root: 1.414214
Within tolerance: True

Play around: repeat with x = 9.0 (root 3.000000) and x = 0.25 (root 0.500000). Check your answers afterwards with x ** 0.5.

Reflection: Why does the loop use a tolerance rather than require guess * guess == x?

Answer: Floating-point values are approximate, so rounding can leave a tiny nonzero error even after the guess stops changing. A positive tolerance defines an acceptable error and lets the algorithm finish when its answer is good enough.


  : Find the peak reading

Difficulty: ★☆☆


Plan first: draw a flow chart that visits every reading, updates the peak only when a larger value is found, and reports the result after the last reading. Trace r, peak before, the decision result and peak after for all five readings. Write the plain-language steps.

Instructions: start the peak at the first reading. Use a for loop and an if statement to find the greatest value; do not use max(). Print the peak to one decimal place after the loop. Assume a non-empty list of numbers.

Expected output: Peak: 14.2.

Play around: try [-5.0, -2.0, -8.0] (expected Peak: -2.0), [7.0] (expected Peak: 7.0) and a list where the largest value occurs more than once.

Reflection: Why should peak start at the first reading rather than at zero?

Answer: Zero might not occur in the data and might be greater than every valid reading. For an all-negative list, starting at zero would produce a false peak. Starting at an actual reading keeps the peak tied to the data.

Difficulty: ★★☆

Instructions: each value in sites is another dictionary containing the site's named fields. Use for name, record in sites.items(): to retrieve each name and record. Print OK when abs(record["error_mm"]) <= record["tolerance_mm"]; otherwise print CHECK. Include the site name in each line.

Reflection: Why is abs() needed when checking a signed measurement error against a tolerance?

Answer: A tolerance bounds the size of the error in either direction. Without abs(), a large negative error such as -0.8 would appear less than a positive tolerance such as 0.5 and could incorrectly pass.

  : Checkpoint — process a measurement log

Difficulty: ★★☆


Plan first (everyone): draw the full flow chart, including the missing-reading branch, peak update, limit check and no-valid-data decision after the loop. Write the plain-language steps. Hand-trace the first four items with columns r, count, skipped, total, peak and above.

Instructions: use a for loop to process the log. None marks missing data: count it as skipped and use continue. For valid numbers, update the total, valid count, peak and count strictly above 13.0. Initialise peak = None and set it from the first valid reading; one possible check is peak is None or r > peak. Print the valid and skipped counts for every test. If there are no valid readings, print No valid readings and do not calculate a mean. Otherwise print the mean to two decimal places, peak to one decimal place, and over-limit count.

Use loops for the calculations, rather than sum(), len(), max(), comprehensions or NumPy. Use descriptive variable names that do not hide built-in functions.
